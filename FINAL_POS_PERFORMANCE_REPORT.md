# DineInk POS — Runtime Performance Report

Scope: runtime performance only — no business logic, API, or visual/UI changes. This is a follow-up to the earlier code-quality pass (`FINAL_POS_CODE_OPTIMIZATION_REPORT.md`), and the first pass to touch `DineIn_Billing.tsx` directly (previously deferred there as high-risk) — but only with memoization/derivation changes that preserve identical JSX output and behavior.

## Key finding that shaped this pass

`vite.config.ts` only wires up `react()` + `tailwindcss()` — `babel-plugin-react-compiler` is installed (`package.json`) but never added to the React plugin's babel config. **React Compiler is not active in this build.** That means manual `useMemo`/`useCallback`/`React.memo` are not redundant here; they have real, measurable effect. This was confirmed before writing any code.

## Billing (highest priority)

**Root cause of "every quantity click re-renders the whole menu grid":** `cart` lived as a plain `useState<any>({})` in `DineIn_Billing.tsx`/`Quick_Takeaway_Billing.tsx`, with `filteredProducts`/`allMenuItems`/`cartItems`/`grandTotal` recomputed unmemoized on every render and `increaseQty`/`decreaseQty`/`bumpCart`/`confirmAddOns` recreated as new closures every render — with zero `React.memo` boundaries anywhere in `components/billing/`. Even if `ProductCard` had been wrapped in `memo`, the constantly-changing handler props would have defeated it immediately.

Changes made, both files (`DineIn_Billing.tsx`, `Quick_Takeaway_Billing.tsx`):
- `filteredProducts`, `allMenuItems`, `cartItems` wrapped in `useMemo` with correct dependency arrays (`Quick_Takeaway_Billing.tsx` already had this for `grandTotal`; extended the same pattern to everything else, and to `DineIn_Billing.tsx` which had none of it).
- New `menuItemsById` — a `Map` built once via `useMemo` — replaces the `allMenuItems.find(...)` linear scan that ran synchronously on every "add item" click.
- `bumpCart`, `increaseQty`, `decreaseQty`, `confirmAddOns` wrapped in `useCallback`. The tricky part: `increaseQty` needs to read the *current* cart to decide whether to open the add-on modal, but depending on `cart` directly would make its identity change on every quantity click — exactly what we're trying to avoid. Fixed with a `cartRef` kept in sync via a `useEffect` (not during render, to satisfy the `react-hooks/refs` rule) and read synchronously inside the callback; `confirmAddOns` similarly reads `addOnModal` via a functional `setAddOnModal` update instead of closing over it directly. Net result: these four handlers now have **fully stable identity** across quantity changes.
- `cartAddOns[itemId] || []` → `cartAddOns[itemId] || EMPTY_ADDONS` (a module-level stable array constant), removing a fresh-`[]`-per-render identity trap.
- `getTableColorState` (`DineIn_Billing.tsx`): was called ~7× per render across the table grid, status-count badges, side panel, and floor-management views — each call independently re-scanning the full `runningOrders` array (O(7 × tables × runningOrders) per render). Replaced with one `useMemo`'d lookup `Map` built in O(tables + runningOrders), computed once per render only when `tables`/`runningOrders` actually change; `getTableColorState` keeps its exact same signature so none of the 7 call sites needed to change.
- Order History panel: per-order `new Date(...).toLocaleTimeString()` calls (placed/done/delivered timestamps) were recomputed inline in JSX on every render, including the 30s poll tick. Now computed once via a `tableOrdersWithTimes` `useMemo`.
- 3 duplicate inline `tableOrders.reduce((s,o)=>s+(o.totalAmount||0),0)` expressions consolidated into one `tableOrdersTotal` useMemo, reused everywhere.
- Fixed the one array-index `key={i}` in the codebase (KOT line-items list) → `key={item.id}`.

**`components/billing/ProductCard.tsx`, `MenuSection.tsx`, `CategoryTabs.tsx`, `CartSection.tsx`, `AddOnSelectorModal.tsx`** — all wrapped in `React.memo`. Combined with the stable handlers/derived-values above: clicking + / − on one item now only re-renders that one `ProductCard`, not the rest of the visible grid. The 30s running-orders poll (`BillingPage.tsx`) still re-renders the page, but no longer cascades into recomputing the menu list or table-color state, since those now bail out on unchanged `useMemo` deps.

## Kitchen Display

- **1-second tick no longer re-renders the whole page.** `now` was top-level `KitchenPage` state ticked every second via `setInterval`, forcing a full re-render of every `OrderCard`, `preparingOrders`, and (in Club view) a full dish-aggregation re-scan — every second, regardless of whether any order actually changed. Extracted a small `ElapsedBadge` component that owns its own 1-second interval; only that badge re-renders each tick now. `now` was removed from `KitchenPage` and from `OrderCard`'s props entirely.
- `OrderCard`, `ClubView`, `AvailabilityView` wrapped in `React.memo`.
- `preparingOrders` wrapped in `useMemo` (deps `[orders]`) instead of recomputing on every render.
- `aggregateByDish` (a full re-scan + sort of every order's items) moved inside `ClubView` behind a `useMemo` keyed on `[orders, processedBatches]` — previously ran unconditionally on every render of `ClubView`, including every 1-second tick.

## Order History / Online Orders

- **Bug found and fixed** (per your go-ahead): `LiveOrdersPage.tsx`'s `filteredOrders` `useMemo` was missing `orders` from its dependency array — clicking "Mark Done" updated `orders` state but the memoized list never recomputed until `search` or the filter pill changed afterward, so the row visibly stuck around. Fixed the dependency array.
- Both `OrdersPage.tsx` and `LiveOrdersPage.tsx` mount a mobile-card tree *and* a desktop-table tree simultaneously (visibility toggled by Tailwind's `xl:hidden`/`hidden xl:block`, not conditional rendering) — so every order/row is actually rendered twice. Per your direction, left that architecture alone (lower risk) and instead extracted each row/card into its own `React.memo`-wrapped component (`OrderMobileCard`/`OrderTableRow` in `OrdersPage.tsx`, `OnlineOrderCard`/`OnlineOrderRow` in `LiveOrdersPage.tsx`), with their handlers (`handleCompleteOrder`, `handleVoidBill`, `openRefundModal`, `handleDirectPrint`, `markDone`, etc.) wrapped in `useCallback`. Now an unrelated state change (typing in the search box, one row's own local button state) no longer forces every other row in both trees to re-render.

## Build / bundle

- **`vite.config.ts`**: added `build.rollupOptions.output.manualChunks` to split stable vendor code (`react`/`react-dom`, `react-router-dom`, `react-redux`/`redux-persist`/`@reduxjs`, `radix-ui`/`@headlessui`) into their own chunks, separate from app code. Pure build config — zero runtime/UI difference. This trades a marginal raw-byte increase (see below) for meaningfully better long-term caching: vendor chunks now keep the same content hash across app-code deploys, so returning users don't re-download React/Redux/Router on every release.
- Total shipped bytes (JS+CSS, `dist/`) stayed essentially flat: **706,036 → 708,342 bytes** (+0.3%) — the small increase is the memoization/extraction boilerplate (new subcomponents, `useCallback`/`useMemo` wrappers) outweighing the code removed (deduplicated `.reduce()` calls, etc.). Despite that, per-feature chunk sizes actually *shrank*: `BillingPage` 107.04 kB → 101.98 kB, `KitchenPage` 16.30 kB → 15.57 kB, `OrdersPage` 16.34 kB → 15.90 kB. The formerly-monolithic 426.72 kB main chunk is now split into `vendor-react` (244.50 kB), `vendor` (127.28 kB, everything else — axios, icon libraries, etc.), `vendor-router` (40.02 kB), `vendor-redux` (20.29 kB), and a much smaller 27.39 kB app-entry chunk.
- Confirmed already-good and left alone: all 6 top-level routes are `lazy()`-loaded behind one `<Suspense>` (`app/router.tsx`); `BillingPage.tsx`'s branch-details/running-orders/add-on-attachments fetch already runs in parallel via `Promise.all`, not sequentially; `lucide-react` imports are all named/tree-shakeable; there are zero `<img>` tags in the app (nothing to lazy-load); `redux-persist` only persists the `auth` slice, so no large-object serialization runs on every dispatch.

## Validated, not changed this pass (recommendations)

- **Redundant polling**: `MainLayout.tsx`, `BillingPage.tsx`, and `KitchenPage.tsx` each independently poll `getAllRunningOrders` every 30s with no shared cache — a non-kitchen user on the Billing page triggers two uncoordinated full-payload requests roughly every 30 seconds (`MainLayout` fetches the entire array just to filter down to `status === "READY"` for the notification bell). Fixing this properly needs a shared data layer (the app already has `zustand` as a dependency, unused — a natural fit) touching all three files at once; flagged as a follow-up rather than done here to keep this pass's blast radius small.
- **Icon library consolidation** (`lucide-react` + `react-icons` + `@heroicons/react` all present) — explicitly skipped: swapping `MdRestaurant`/`FaFire`/heroicons for lucide equivalents risks a visible glyph/sizing difference, which conflicts with "do not change UI."
- **Lazy-loading ManageShop's 4 tabs** — skipped per your answer; the chunk is already small (32.31 kB) and route-level-lazy, not worth a new loading-flash.
- **OrdersPage/LiveOrdersPage's dual mobile+desktop mounted trees** — the row-memoization above makes this much cheaper, but the underlying "both trees always mounted" architecture is unchanged; switching to JS-conditional single-tree rendering was explicitly deferred per your answer (small resize/orientation-change risk).
- Order History (`OrdersPage.tsx`) and Expense history (`Expense.tsx`) still have no virtualization/pagination for what could become a long list over time (`Inventry.tsx` already paginates at 20/page as a working model to copy) — not applied this pass since it wasn't in the approved plan; noted for a future pass if list sizes grow.

## Verification

- `npx tsc -b` — clean throughout.
- `npm run lint` — compared via `git stash` before/after (same methodology as the prior pass): 238 → 244 problems. Checked by rule category, not just raw count: every category is one that already existed pre-pass (`@typescript-eslint/no-explicit-any`, `react-hooks/set-state-in-effect`, `react-hooks/exhaustive-deps`, `react-hooks/preserve-manual-memoization`, `react-hooks/refs`, `react-hooks/purity`, `no-control-regex`) — no new category was introduced, and one pre-existing warning (`react-hooks/set-state-in-render`) actually disappeared. The one genuine new issue this pass introduced along the way — writing to `cartRef.current` directly during render, flagged by `react-hooks/refs` — was caught by this same lint check and fixed (moved the sync into a `useEffect`) before finishing.
- `npm run build` — succeeds; chunk sizes reported above.
- Dev server starts and serves without console/build errors. As before, full interactive click-through (adding items, changing quantities, switching tables, completing a checkout) was **not** performed — this environment has no running backend/credentials and no browser-automation tool available. The memoization changes were verified by reading the rendered JSX/logic before and after each edit to confirm identical output; a manual pass on a real device/browser (rapid-tapping quantity buttons on a menu with realistic item counts, and switching tables back and forth) is recommended before relying on this as a performance fix in production.
